# Open Tasks

Everything not yet implemented.

**Keep this file sorted by task number**: the table and the descriptions below it, both in ascending order. A new task goes at its numeric place in each (a gap is fine; take the next free number across this file and `TASKS-DONE.md`).
Every row has a priority after its number: High, Medium or Low.
Add a summary to the table, then details under Descriptions.

Rules for tasks:

* Keep tasks atomic: work with no dependency between its parts is listed as separate tasks.
* Avoid overlap and "parent tasks":
  * Clearly mark if a task requires another one to start (*Needs:*).
  * Don't keep task A open waiting for task B to finish if no work is left in A that depends on B.
  * The same work is not duplicated across several tasks.

Gaps found while working on the base game are added here as new tasks, not left in notes.

Finished tasks are moved to [`TASKS-DONE.md`](TASKS-DONE.md) with
`python3 scripts/archive_done_tasks.py` (a task is done when its row and its title both say "(done)").

## Descriptions

**95. Tutorial.** A first-game guide: highlighted steps for moving, founding a city, building,
researching and casting, with a way to skip or switch it off.

**115. Cityscape: road masking.** The city picture draws the whole road grid; the original hides the road squares that no building, house or tree touches (`Cityscape_Roads_1` to `_5` in ReMoM `CITYSCAP.c`, using the road pictures and the two masks `cityscap.lbx` 109 and 110), so roads appear only where the city has grown. Port the masking rules.

**172. Learning AI: battle AI follow-ups.** What tasks 170 and 171 left (`learning-ai.md` 7.7 and 7.8): (1) stronger yardsticks than the scripted AI, which random orders already beat: past checkpoints as opponents (the league of 6.4), Elo, and an evaluation as the defender; (2) the agent chooses **which unit** moves (a pointer over the units) and can cast later in the turn, not only at its start; (3) fleeing: it is found only with the help of a head that compares the value of fleeing with the critic's, and it still flees in fights it would win; (4) longer runs and a checkpoint chosen by its held-out score; (5) the AI wizards' real battles as training data (task 8.3), difficulty levels from checkpoints, and a client setting for `--battle-ai` (the client needs the `learned` feature and a checkpoint file); (6) the battle outcome model for the strategic AI (8.4); (7) a gap the first runs show: the odds classes were measured with the scripted AI, so a better player makes them easy. (8) The bank was made before the undead, experience and neutral-unit changes of 13 October, and no run has trained on **Animate Dead** (the agent can now aim it: the fallen have tokens); remake the bank and train again. Remaking the bank also picks up the 11 spells of eligibility 2 and 3 that are castable in battle now (task 55).

**176. Installer.** The setup program `f4x-setup` (Rust, no Python, no toolchain on the player's machine): finds the player's copy of the original, extracts art, sound and music into the data folder, with the MT-32 ROM step. Design and decisions: `docs/installer-design.md` (sections 3, 6, 7 and 8). The author tests it by running it on this Mac. *Done so far (16 November 2026):* the data-folder lookup, pictures, sound effects, MT-32 ROM step (download or own folder), music rendering (`f4x-music`), the windows and the Setup app in the dmg. The release workflow `.github/workflows/release.yml` is written (tag `vX.Y.Z`), not yet run. The Linux package is built too (`scripts/make_linux.sh`, a release job, the first-start dialog through `zenity`) and `docs/` has install guides for Mac and Linux. *Left:* the author's manual run of the dialogs and the dmg through Gatekeeper, the first tagged release run, clicking through the game's first-start dialog, a GOG copy (unverified: nobody here has one).

**291. Variant river pictures for the battlefield (low priority).** Each river shape has two pictures in the original, a first variant (`cmbtcity` 97 to 102) and a second (103 to 108), chosen at random per square (`56 + 6 * variant + shape` in `Look::tiles`). The shipped files hold only the second variant, and Myrror's `chriver` 0 to 11 are empty, so every river square of a shape looks the same (`river_art.rs`, `crates/f4x-client/assets/rivers/`). Make a first variant by mirroring or rotating the existing six pictures (a left-right piece mirrored is up-down in the other diagonal, corners swap in pairs; check each against a screenshot so the banks still join), generate it once for both planes, keep the PNG files in `assets/rivers/` like the others, and have `river_art.png` pick the variant from the tile number. Until then the client takes the shape from `tile % 6` and ignores the variant. Asked for by the user, 17 October 2026; follows task 255, now archived.

A missing rule goes to task 350 or a task of its own; the text is a key in `crates/f4x-client/content/text/`.

**365. Crossfade the music.** Ours; the original stops all sound and starts the next piece. Fade the old track out and
the new one in over about a second when the music changes (a screen, a battle, a short piece and back to the
background), so the changes are less abrupt; short pieces fade the background out and in again on their own end.
`Audio::music` in `crates/f4x-client/src/audio.rs` is the one place that changes tracks; macroquad's audio has
`set_sound_volume`, so the fade is volume steps per frame on the two sounds, and the old sound is kept loaded until it is
silent. A switch under Settings ("Fade Music") turns it off for those who want the original's cuts.

**725. Audit the code base for needless call chains.** Found on 20 November 2026 while sizing task 718: the AI's `unit_strength(view, u)` calls `PlayerView::unit_power`, which calls `UnitView::unit_power` (`unit/mod.rs`), which calls `battle::power::unit_power`: four functions for one measure, three of them forwarding. A function should get its information directly at the source, and a layer in between must serve a purpose: it wraps private data (the caller may not see the field), converts data (a type or a unit), is an access helper that saves the caller from knowing where something lives or a set of arguments it would repeat, caches, or enforces a rule (a permission, a fog-of-war filter). A layer that only passes its arguments on, renames the call, or exists because it once did something else is removed and its callers go to the source. Audit the crates (`f4x-core`, `f4x-ai`, `f4x-client`, `f4x-tools`): (1) list the forwarding functions (a body that is one call with the same arguments, methods that call a method of the same name on a field or on `self.game`, free functions that wrap a method), and the chains of three or more layers; (2) for each, say which purpose it serves (name it in the doc comment when it is a real one, as `PlayerView` does for fog of war) or remove it and update the callers; (3) take care that a layer which looks like forwarding but filters what the AI may see (`PlayerView`) stays, and that the crate rules of `docs/design.md` section 2 about who may depend on whom still hold after the change; (4) write down what was found in `docs/KNOWLEDGE.md` and the rule, a layer needs a stated purpose, in `docs/rust_coding_rules.md`. Do it module by module with the tests green in between; no change of behaviour (soak before and after for the AI crates). Task 718 and 720 meet the first example, and are the place to flatten it. *Needs:* nothing.
