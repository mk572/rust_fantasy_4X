## Descriptions

**390. Standard buttons and hit-testing.** `ui::button` is called about 83 times, and about 105 places test `mouse_position()` against a rectangle by hand (picture buttons and screens in the original's coordinates each repeat hover, press and disabled states). Add one helper in `ui.rs` that takes a rect in layout space and returns `None`, `Hover`, `Pressed` or `Clicked`, maps the mouse through `Layout` in one place, and covers text buttons, picture buttons and art-less hot-zones. Give it right-click help, the hotkey label and the disabled-reason tooltip (as the Buy button's refusal text) so screens stop doing these by hand. **Done in part:** `ui::hit(rect, enabled, input)` returns `Hit` (`None`, `Hover`, `Pressed`, `Clicked`). `ui::button`, every picture button (one `App::pic_button` in `frame.rs` with a `Disabled` look, wrapped by the city, army, unit, options, city-list and battle-bar buttons), the text buttons of the menu, new-game and autobuild screens, the book screens' click areas and the plain click-in-rectangle tests of the city, magic, production and unit screens use it. **Also done:** the remaining hot-zones (craft, item, advisor, new-game, road plan, surveyor, diplomacy, the yes/no prompts, list-cell scans, the frame's menu and Next Turn) now use `ui::hit` or `pic_button`, each keeping its own gating as the `enabled` argument; no `rect.contains(mouse)` is left outside `ui::hit`. A test (`hit_answers_what_the_hand_written_tests_did`) pins that `hit` answers what the hand-written tests did. The draw side of the picture buttons cannot be unit-tested without textures; it was checked on screenshots (main frame, vault). Right-click help already has its one place, `watch_for_help` against the table in `content/help.ron`. The hotkey label and the disabled-reason tooltip moved to task 416.

**393. Textures and scaling.** Find out with a profile whether any pictures are rebuilt from `Image` each frame instead of kept as `Texture2D`. **394. Screen trait.** `Screen` is an enum and `view.rs` is large. Give each screen one implementation of a `Screen` trait (`update`, `draw`) so `view.rs` becomes the dispatcher and fewer files know about each other. Do this after 389 and 391. **Started:** the dispatch is now one function, `App::screen_frame` in `view.rs` (the `match` on `Screen`), which `frame()` and the modal base both call. The screens are still `App` methods with their state in `App` fields (`big_ui`, `diplo_ui`, `city_list_ui` and so on), so the trait needs each screen's state moved into its own struct first. **Pilot done:** `page.rs` has the `Page` trait (`frame(&mut self, app, input)`), `App::open_page` and `App::page_frame` (the page is taken out of `App.page` for the frame, kept while the screen is the same, dropped when it changes). Hall of fame (`HallPage`, owns its table), settings (`SettingsPage`, no state of its own; `open_settings`), the creation wizard (`CreateState` is the page; its step methods are `impl CreateState` taking `app`, so `create` left `App`) the army list (`ArmyUi`) and city list (`CityListUi`), where the existing `*Ui` struct is the page, the wizard sheet (`WizardUi`), the magic screen (`MagicUi`; `open_magic_alchemy` for the item screen's button), the item screen (`ItemUi`; its methods that touch the state are `impl ItemUi` taking `app`), the outpost (`OutpostUi` plus its city; `Page::music` replaces audio reading `outpost_ui`), and enemy city (`EnemyCityPage`, owns its city; `Screen::EnemyCity` lost its payload) are converted. The rest follow the same recipe: state into the page, `self.` to `app.`, `open_x` calls `open_page`.

**410. Food consumption of a unit as a field of the unit table.** The food a unit eats is a rule in the code (every normal unit eats 1 food, heroes and summoned creatures eat none), not a number of the unit. `Upkeep` in `units.ron` already has a `food` field, which the data leaves empty, so a mod cannot say that a unit eats more, less or nothing. Put the food in the unit table: set `food` in the `upkeep` of every unit that eats, **in half units like moves** (2 means the unit eats 1 food, 1 means half a food, so a mod can set finer values; the normal units get 2; the city's balance adds the half units up and converts at the end, so check how an odd total rounds and state it in `docs/design.md`; check the original's rule for the units it exempts, and `docs/design.md`), make the city's food balance and the unit's upkeep read that field instead of the unit's kind, and drop the kind-based rule. Cover it with a test that walks every unit (as the tests of task 404 do): a unit eats what its row says, and the totals of a saved game do not change. Note the new field in `docs/ecs-structure.md` or the modding notes if there are any.

Check in ReMoM what the original does with the target (`Cast_Floating_Island`-like code in `OverSpel.c`) so the placement rule stays the original's.
